# SyncLab — Interactive Synchronous and Asynchronous Execution Simulator

## Abstract

Independent requests often spend time traveling to a service, waiting for service completion and returning to a caller. A sequential client waits through those phases before sending its next request. A concurrent client can admit other independent work during that interval. SyncLab makes the distinction observable through deterministic schedules, process-level traces and calculated metrics. In the five-request default workload, allowing three outstanding requests changed completion time from 5,330 to 2,250 virtual milliseconds. Total modeled communication remained 1,180 ms in both schedules. The experiment isolates the effect of overlap without relying on browser timer accuracy.

## 1. Introduction and problem definition

The official problem statement is “Develop a project comparing synchronous and asynchronous execution using simulated processes, communication delays, and response mechanisms.” A simple animation cannot establish why a process finished earlier. The educational requirement is to reconstruct every visible phase and reported result from the input workload. This design therefore computes a deterministic event history and uses animation only for replay.

The objectives are to visualize blocking, demonstrate out-of-order completion, distinguish communication time from queueing time, and evaluate how delivery and recovery rules alter measured outcomes.

## 2. Requirements and method

The experiment varies admission policy while holding process definitions, transport times and response mechanism constant. Each logical process has a stable ID. It may arrive after time zero and may contain multiple attempts. The client has one sequential slot or a bounded pool of asynchronous slots.

The independent variables are process durations and arrival times, communication delays, slot count, response mechanism, delivery overhead, deadlines and retry settings. The measured variables include workload completion time, per-process response, waiting time, successful throughput, outcome counts, peak occupancy and terminal order. The user can reproduce an experiment by saving its inputs and exporting its event history.

## 3. System design

The project uses a frontend-only architecture. The engine computes two schedules from the same validated input. A run contains ordered events, half-open intervals, logical terminal records and summary statistics. React components own editing and navigation. A playback hook owns only the virtual cursor, active state and speed. Recharts renders the comparison from the generated records. The architecture diagram is in [ARCHITECTURE.md](ARCHITECTURE.md).

Dispatch is a scheduling decision. Transport arrival is a communication event. Detection by the client is a separate delivery decision. Keeping these separate makes it possible to represent a response that has reached the transport but is still waiting for a poll or notification.

## 4. Implementation

The scheduler selects the earliest eligible request and earliest available slot. It computes the attempt's transport and processing boundaries, applies the delivery rule, and clips intervals at timeout. If the attempt can retry, a new eligibility time includes the configured backoff. A synchronous retry retains the caller's turn. An asynchronous retry frees the slot for unrelated eligible work.

Events are identified by process, attempt and deterministic insertion sequence. This allows a late reply to be logged without changing a newer attempt's outcome. The playback hook maps elapsed frame time into virtual time. Pause and step do not regenerate the schedule.

The interface supports a full scheduled view before playback and a filtered event prefix during playback. A process inspector combines live state with the complete scheduled trace. Exported CSV rows represent logical processes. JSON contains the configuration, units, metrics and both event streams.

## 5. Experimental results

The table was generated by executing the included scheduler against each unchanged preset. Times are virtual milliseconds. Each experiment uses the preset's three async slots.

| Workload                     | Synchronous finish | Asynchronous finish | Difference |
| ---------------------------- | -----------------: | ------------------: | ---------: |
| Mixed Workload               |              5,330 |               2,250 |      3,080 |
| Low Latency                  |              4,250 |               1,840 |      2,410 |
| High Latency                 |             11,150 |               4,600 |      6,550 |
| Slow Server                  |             17,780 |               7,650 |     10,130 |
| Unpredictable Response Order |              4,405 |               2,170 |      2,235 |
| Failure and Timeout Scenario |              8,010 |               3,800 |      4,210 |

In Mixed Workload, P1 occupies an async slot from 0 to 840 ms. P4 then occupies that slot until 1,440 ms. P3, admitted at time zero, continues until 1,640 ms. Consequently P4 finishes ahead of P3. The synchronous order stays P1, P2, P3, P4, P5. Average response falls from 3,204 to 1,464 ms, and mean waiting falls from 2,138 to 398 ms.

In the fault preset, both schedules produce three successes, one failure and one timeout. P1 succeeds on retry. P3 exceeds the deadline on both attempts. P5 reports an injected failure on both attempts. Counting the final attempts as extra completed processes would inflate throughput, so throughput uses the three successful logical records. Late replies can extend playback after the logical workload has ended.

As a control, a single independent 100 ms request with no transport delays and direct delivery finishes at 100 ms in both models. With two independent 100 and 40 ms requests, the sequential total is 140 ms and the two-slot total is 100 ms. These small workloads support hand calculation and regression testing.

## 6. Verification

Automated tests cover sequential dispatch, overlap, capacity, tie ordering, exact polling boundaries, clipped communication, deadlines, recovery, late replies, metrics, persistence, editing and playback. A real browser exercise verified the integration from editing through downloads. Phone and tablet checks used viewports of 320, 390 and 768 pixels. The packaged standalone browser runner and its execution limitation are documented in [TESTING.md](TESTING.md).

## 7. Limitations and further work

The system assumes independent services with no shared CPU or bandwidth bottleneck. The event queue models delivery delay without a contended consumer. Fixed process times support repeatable comparisons. A separate live Promise experiment measures browser wall time, which varies with real scheduling.

A finite server-worker pool would let future experiments explore contention. A dependency graph could model workflows in which the next request consumes the previous response. Seeded latency distributions and repeated trials could support statistical comparisons while retaining identical realizations across the two models.

## 8. Conclusion

The reference experiments demonstrate that overlapping waiting intervals can shorten workload completion without reducing total communication volume. The single-request control and one-slot success-only control identify configurations in which the models coincide. Per-attempt traces explain changes in ordering and recovery, allowing students to defend a result using recorded events.
